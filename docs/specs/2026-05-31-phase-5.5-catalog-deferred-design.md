# Phase 5.5 Catalog Deferred Entities — Design Spec

## Goal

Close the 10 entities Phase 5 FD#5 deferred (ProductSupplier, ProductSupplierPreference, ProductPackage, ProductPrice, ProductCatalog, ProductCatalogItem, ProductAttribute, ProductAssociation, ProductComponent, UnitOfMeasureConversion) by extending the existing catalog-service to own them. Honors the RC-11 breadcrumb commitment by adding Category writes. Partially closes RC-13 (3 of 5 CategoryApiController refs deletable without inventory dependency). Tag `phase-5.5-catalog-deferred` when done.

## Background

Phase 5 (`phase-5-catalog` tag at `c5f531851`) extracted 9 catalog reference-data entities to a new `services/catalog-service/` Spring Boot module. Phase 5's FD#5 explicitly deferred 13 entities — **10** to Phase 5.5 (this spec) and **3** to natural owning phases (ProductAvailability + ProductMergeLogger → Phase 6 inventory; ProductSummary → Phase 11 reporting or never since it is a SQL view).

Phase 5.5 is **not** a new service extraction — it extends the existing `services/catalog-service/` module. No new Gradle subproject, no new auth infrastructure (Phase 5.1 already shipped `services/jwt-auth-common`; verified at `services/catalog-service/build.gradle:14`). Phase 5.2 codified the plan-defect lessons (sdd-reviewer-checklist.md + plan-template-defects.md + README.md); those guardrails apply to plan-write here. The work is per-entity: entity port → DTO → service → controller → cache (where applicable) → tests → nginx routing → Grails-side caller migration, per the parent design §8 per-slice template, scoped to the existing catalog-service module rather than a fresh one.

The RC-11 breadcrumb in `services/catalog-service/src/main/java/org/openboxes/catalog/cache/CategoryCache.java:40-41` (added in Phase 5.1 T10 at commit `1a6799498`) explicitly anticipated Phase 5.5 would add Category writes: the comment says "expose publicly when CategoryService.save() introduces a write flow that needs cache refresh." Phase 5.5 honors this by adding POST/PUT/DELETE on `/api/category` + `CategoryService.save()/update()/delete()` + reverting `CategoryCache.refresh()` to `public` for cache-on-write invalidation. The `CategoryCache.clear()` method (`CategoryCache.java:49`, public) was already added in Phase 5.1 T10 RC-12.

## Approach

**Single phase, full SDD cadence** per Phase 5 retro line 215 ("Phase 5.5 (13 deferred entities) per full SDD cadence given scope size"). Mirrors the Phase 5 task structure verbatim: T1 audit + 1 task per deferred entity (T2-T11) + Category writes task (T12) + partial RC-13 task (T13) + done-gate (T14). ~14 SDD tasks. Per-task user-enforced stop-after-each-task gate. Two-stage per-task review (spec-compliance + code-quality) per established Phase 4/5 cadence.

Cross-service FKs (ProductSupplier → Organization×2 for supplier + manufacturer; all audit fields → User in identity-service) stay at the DTO level as flat IDs only (no nested objects, no service-side HTTP from catalog to org or identity). React handles joins client-side per Phase 5 FD#3 flat-FK-only DTO pattern. This keeps catalog-service free of new cross-service HTTP dependencies; service-side HTTP coupling can be added later if a concrete consumer requires it.

**Rule 3** (nginx prefix-match silently captures Grails sub-routes, codified in `docs/process/plan-ordering-rules.md:32`) applies. Per A12 verification: only ProductSupplier currently has a codified Grails sub-route (`"/api/productSuppliers/export"` at `UrlMappings.groovy:911`); ProductPackage has none despite the retro line 114 speculation. T1 audit re-runs the Rule 3 grep per entity to catch any sub-routes I missed.

**Approaches rejected:** family-batching loses per-entity revertibility within families; risk-weighted reordering inconsistent and harder to plan-review (see brainstorming Q1 alternatives).

## Forced design decisions

### FD#1 — Per-entity write scope: T1-audit-driven

Mirrors Phase 5 FD#1. Default GET-only for all 10 entities; POST/PUT/DELETE added per `(entity, verb)` where T1 audit finds React callers in `src/js/**/*.{js,jsx,ts,tsx}` for inline `/api/*` strings + Grails-side `*ApiController.groovy` actions. Pre-declared in this spec only when explicitly known:

- **ProductSupplier**: CRUD per Phase 5 FD#5 ("React-driven CRUD exists in `src/js/api/services/ProductSupplier*Api.js`")
- **ProductPackage**: POST per Phase 5 FD#5 ("React POST exists")
- **Category**: full CRUD per FD#3 of this spec

All others — T1 decides.

### FD#2 — All cross-service FKs are flat ID-only at DTO level

Cross-service FKs identified in Phase 5.5 scope (per A3 verification):

- **ProductSupplier → Organization×2** (`supplier` + `manufacturer` at `ProductSupplier.groovy:45,52`) → organization-service
- **All entities with audit fields** (`createdBy`, `updatedBy` of type `User`) → identity-service. Found on ProductSupplier, ProductPackage, ProductPrice (per A2/A3/A4 reads); T1 enumerates the rest.
- **(Reference only, not new):** Product, Attribute, UnitOfMeasure, Category — all intra-catalog (no cross-service hop).

**Resolution:** all cross-service FKs are exposed as flat string IDs in DTOs (`supplierId`, `manufacturerId`, `createdById`, `updatedById`). No nested objects in DTOs. No service-side HTTP from catalog-service to org-service or identity-service. React calls `/api/suppliers/{id}` on org-service or `/api/users/{id}` on identity-service separately when needed. Consistent with Phase 5 FD#3 flat-FK-only DTO pattern.

**Why no service-side HTTP yet:** catalog-service has no current business logic requiring validation that `supplier_id` resolves in org-service (admin-supervised data entry; trust callers). Adding service-side HTTP can happen later if a concrete consumer requires it; YAGNI now.

### FD#3 — Category writes scope: full CRUD

Per RC-11 breadcrumb in `CategoryCache.java:40`. Phase 5.5 adds POST/PUT/DELETE endpoints to catalog-service `CategoryController.java` (file is named `CategoryController.java`, NOT `CategoryApiController.java` — per A8). New `CategoryService.save()/update()/delete()` methods invoke `categoryCache.clear()` after each successful write (the public `clear()` was already added in Phase 5.1 T10 RC-12). Revert `CategoryCache.refresh()` to `public` (it is currently package-private per A6) and remove the "exposed publicly when CategoryService.save() lands at Phase 5.5" breadcrumb comment since the commitment is now fulfilled.

Category writes race with Grails-side `CategoryController.groovy` admin actions (per A14: `static allowedMethods = [save: "POST", update: "POST", delete: "POST"]` + `saveCategory()` + `deleteCategory()` write via `categoryGormService`). T1 audit applies the FD#5 write-race protocol to Category specifically.

### FD#5 — Concurrent-write race per entity: defer to T1 audit

Mirrors Phase 5 FD#9 pattern. For each entity where Phase 5.5 adds writes AND a Grails-side writer also exists, T1 audit:
1. Identifies whether the underlying table has unique constraints protecting against silent duplicates (`SHOW CREATE TABLE <entity_table>`)
2. Identifies whether app-layer protection is needed (e.g., cross-instance uniqueness checks à la Phase 5 FD#10 for Synonym)

Forced decision options per entity (T1 resolves): accept-silent-duplicates / app-layer pair-uniqueness check in service / escalate to per-entity Phase X / app-layer optimistic-lock retry.

Entities with confirmed Grails-side writers (per A14 + Phase 5 FD#1):
- **Category** (writes added in T12; Grails CategoryController has admin save/update/delete per A14)
- **ProductPackage** (Grails ProductPackageController has admin actions per Phase 5 FD#1)
- **ProductSupplier** (Grails admin actions per Phase 5 FD#1)
- Others — T1 enumerates

### FD#6 — Cache strategy per entity: apply FD#7 churn-frequency heuristic at plan-write

Mirrors Phase 5 FD#7. Final per-entity decision at plan-write per T1 audit signal. Tentative classifications:

- **Cache (mature reference data, rare changes):** UnitOfMeasureConversion (paired with cached UoM); ProductAttribute if T1 finds low churn
- **Cache with refresh (mid-churn):** ProductCatalog (has `cache true` GORM hint per A5 read), Category (already cached, write-invalidation added in T12)
- **No cache (higher churn or large):** ProductSupplier, ProductSupplierPreference, ProductPackage, ProductPrice, ProductAssociation, ProductComponent

T1 verifies dev-DB row counts (acknowledging they are not reliable per Phase 5 FD#7) and consults real admin-UI churn patterns when available.

### FD#7 — ProductAttribute 4-way FK: standard JPA bidirectional

Per A2 read: ProductAttribute has `belongsTo = [product: Product]` plus three nullable `@ManyToOne` references — `Attribute attribute`, `ProductSupplier productSupplier`, `UnitOfMeasure unitOfMeasure`. All 4 FKs are intra-catalog-service (no cross-service issue). Standard JPA `@ManyToOne` for each; `belongsTo Product` becomes `@ManyToOne(optional=false)` with cascade.

DTO is flat (4 FK IDs: `productId`, `attributeId`, `productSupplierId`, `unitOfMeasureId`). N+1 query awareness during list endpoints — use `@EntityGraph` or explicit `JOIN FETCH` when listing many ProductAttributes; integration test asserts bounded query count. Otherwise no special handling.

**Task ordering implication:** T8 (ProductAttribute) depends on T2 (ProductSupplier) having landed for the PS FK.

### FD#8 — Grails GORM audit hooks: JPA @EntityListeners + CurrentUserService pattern

Per verification reads, ProductSupplier (lines 92-99), ProductPackage (lines 23-30), ProductPrice (lines 18-25) all have `beforeInsert/beforeUpdate` GORM hooks that set `createdBy = AuthService.currentUser`, `updatedBy = AuthService.currentUser`. JPA does not support GORM-style hooks; the standard replacement is `@EntityListeners(AuditingEntityListener.class)` with a `Supplier<String>` (or analog) providing the current user.

**Pattern reuse, not invent:** Phases 3-4 (location-service, organization-service) already shipped audit-field handling in their entities (verified at plan-write by reading existing org-service/location-service audit infrastructure). T1 audit identifies the established pattern and reuses; if no established pattern exists in catalog-service yet, T1 surfaces this as a forced decision (build pattern in catalog-service now, or postpone audit fields to a later phase).

`Date dateCreated / Date lastUpdated` (GORM auto-set) → standard `@CreatedDate / @LastModifiedDate` with `@EnableJpaAuditing` — already mature infrastructure.

### FD#9 — Saga implications: NONE (explicit non-issue note)

All 10 entity write paths are intra-catalog-service. Cross-service references (ProductSupplier → Organization×2; audit User FKs) are reads-only via React-client-join per FD#2, not writes. Phase 5.5 lands pre-Phase-7; saga infrastructure (parent design §4.5 outbox + relay + subscriber framework) is not built yet.

If T1 audit surfaces an unexpected cross-context atomic write expectation (e.g., catalog-service needs to update an org-service column inside its own transaction), forced decision: defer-that-entity-to-Phase-7-or-later OR add restructure to make write local. Do not invent ad-hoc cross-service writes.

## Risks

- **T1 audit surfaces unexpected cross-context atomic writes** for one of the 10 entities. Phase 5.5 lands pre-Phase-7, so saga infrastructure is not built. *Mitigation:* per FD#9, that entity defers to Phase 7+ and Phase 5.5 ships the remaining 9. Bounded.
- **ProductSupplier's Organization×2 FKs don't resolve cleanly.** Phase 4 extracted Organization (with party-role flavors for Supplier/Manufacturer); column shape may have drifted. *Mitigation:* T1 audit runs `DESCRIBE product_supplier` against the running DB + cross-checks Phase 4 migrations; surfaces a forced decision if `supplier_id` / `manufacturer_id` column types don't match Organization.id type (already verified as CHAR(38) per A3 migration grep).
- **ProductPrice's bidirectional `belongsTo [productPackage, productSupplier]` complicates JPA mapping.** GORM `belongsTo` is dependency + cascade syntax; JPA doesn't have a 1:1 equivalent. *Mitigation:* T5 maps both as nullable `@ManyToOne` FKs (no cascade from owner side; ProductPrice is independent in the JPA sense). Integration test asserts orphan ProductPrice rows can be deleted directly without cascade interference.
- **ProductAttribute's 4-way FK causes N+1 query explosion** on list endpoints (`/api/productAttributes`). *Mitigation:* T8 uses `@EntityGraph` or explicit `JOIN FETCH` on list queries; integration test asserts bounded query count; spec-reviewer reviews query patterns at T8.
- **Category writes race with Grails-side `CategoryController.groovy` admin** writes (confirmed real per A14). *Mitigation:* FD#5 deferred to T1 audit; T1 verifies `SHOW CREATE TABLE category` for unique constraints + identifies whether `parent_category_id` self-FK has cycle protection. Forced decision at T1 if unsafe.
- **Audit-field pattern reuse fails** — Phases 3-4 may not have shipped a clean reusable pattern; catalog-service has to build it fresh in Phase 5.5. *Mitigation:* T1 audit identifies the established pattern explicitly (read org-service / location-service entity files); if none exists, surfaces as forced decision (build-now / postpone audit fields).
- **Rule 3 sub-route audit misses a Grails sub-route** despite the A12 finding of only `/api/productSuppliers/export`. *Mitigation:* T1 reruns the Rule 3 grep per entity; per-entity smoke includes explicit curl for every Grails-stays sub-route per Rule 3 done-state.
