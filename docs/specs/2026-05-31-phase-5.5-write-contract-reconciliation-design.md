# Phase 5.5 Write-Contract Reconciliation — Design

- **Date:** 2026-05-31
- **Status:** Design (awaiting critical-design-review)
- **Parent spec:** `docs/specs/2026-05-31-phase-5.5-catalog-deferred-design.md`
- **Parent migration design:** `docs/specs/2026-05-25-grails-to-spring-boot-migration-design.md`
- **Plan to be re-sequenced:** `docs/plans/2026-05-31-phase-5.5-catalog-deferred-implementation-plan.md`
- **Triggering commit:** `1c8557561` (T2 ProductSupplier)

## 1. Problem

Phase 5.5 T2 migrated `ProductSupplier` to catalog-service with a **flat, FK-only DTO** per the
parent spec's FD#2/FD#3 (`productId`, `supplierId`, `manufacturerId`, … as raw `char(38)` id
strings) and repointed nginx so `/api/productSuppliers` (all methods) now resolves to
catalog-service. **This shipped a regression**: the real React ProductSupplier form is a composite
aggregate whose read and write shapes are both incompatible with the flat contract.

**Read side.** The form loads from one Grails `toJson` GET and reads **nested objects**:
`productSupplier.product.{id,name,productCode}`, `productSupplier.supplier.{id,name,code}`,
`productSupplier.manufacturer.{id,name}`, plus nested `productSupplierPreferences`
(`useProductSupplierForm.js:62-95`). The flat DTO returns ids only, so every dropdown loads empty
on edit.

**Write side.** The form's save fans out to **four** endpoints in sequence
(`useProductSupplierForm.js:307-338`): details → package → preferences → attributes. The details
payload sends **Grails association-name keys** (`product`, `supplier`, `manufacturer`,
`ratingTypeCode` as id strings — `buildDetailsPayload:214-217`), not the flat DTO's `productId`/
`supplierId`/`manufacturerId`. So writes to catalog-service fail.

**Why the T2 tests passed anyway.** The T2 integration tests and Playwright e2e used **synthetic
flat JSON** that matched the DTO but never matched the real React shapes. That blind spot is the
root cause this correction exists to codify (see §8).

**Why one entity can't cut over alone.** The save fan-out spans `ProductSupplier` (T2),
`ProductSupplierPreference` (T3), `ProductPackage` (T4), and `ProductPrice` (T5 — the contract
price, persisted via the package endpoint's payload), plus `ProductSupplierAttribute` (stays on
Grails — not among the 10 migrated entities). The form can only switch its API seam to
catalog-service **once the whole supplier cluster (T2+T3+T4+T5) exists there**. Migrating T3/T4/T5
the same way T2 was done would compound the live regression with each commit.

## 2. Decision

**The flat catalog-service contract stays; the React side moves to it.** This is what the parent
design's vertical-slice rule always intended ("migrate backend AND frontend together"). React
remains Grails-hosted — only its API seam (load mapping + save payload) changes. SPA decoupling
stays deferred to Phase 12 (parent design A19).

This is a **design-level correction**, not a quick patch: it contradicts shipped T2, reshapes the
remaining cluster tasks, and adds a cluster-end cutover. It needs a spec + review before execution.

## 3. Immediate corrections (forward commits now)

These land as **forward commits** — T2 is **not** amended. Keeping the repoint-then-revert in
history is a deliberate lessons-learned trail.

1. **Revert T2's nginx repoint.** Remove the three `/api/productSuppliers*` blocks
   (`docker/nginx/conf.d/app.conf:135-149`) so `/api/productSuppliers` falls through to the Grails
   `/api/` catch-all (`:151`). The live form works again. The catalog-service `ProductSupplier`
   backend (entity, DTO, service, controller, repository, audit infra) is **kept** — only the
   routing reverts. The through-nginx Playwright e2e for productSuppliers is parked (`test.skip`)
   until the cluster-end cutover re-enables routing.

2. **Fix the misleading 401 on failed catalog writes.** Add a catalog-service
   `@RestControllerAdvice` that maps write-path exceptions to honest status codes:
   `DataIntegrityViolationException` → **409**, bad/missing input
   (e.g. `MethodArgumentNotValidException`, `HttpMessageNotReadableException`) → **400**. This
   follows the identity-service precedent (`GlobalExceptionHandler.java:20-31`, same Spring
   Security setup). Needed **before T3**, whose pair-uniqueness rejection must surface as a real
   4xx rather than a masked 401. The 401 mechanism is described accurately in §6.

3. **Lessons-learned note** in `docs/process/` capturing the synthetic-payload blind spot: a
   migration is only proven when tested against the **real** frontend payload shapes, not against
   synthetic JSON shaped to the new DTO.

## 4. Reshaped cluster tasks (T3 / T4 / T5)

T3 (`ProductSupplierPreference`), T4 (`ProductPackage`), and T5 (`ProductPrice`)
become **backend + integration tests only**:

- No per-task nginx repoint.
- No per-task React change.
- No per-task through-nginx e2e.

They all feed the one composite form, which does not cut over until the cluster is complete. Each
keeps its per-task two-stage review gate (spec-compliance + code-quality) per the established Phase
5.5 cadence. Entity-specific gotchas already surfaced (e.g. T3's `@Version` mapping on
`product_supplier_preference.version`, nullable audit columns, flat `preferenceTypeId`, two-part
pair-uniqueness) carry into the re-sequenced plan, not this design.

## 5. New backend list-query sub-task (before cutover)

The cutover must serve the **list page**, not just the form. The list page
(`useProductSupplierListTableData.jsx:25-38`, `useTableData.jsx:60-91`):

- Sends filter params `product`, `supplier`, `defaultPreferenceTypes` (ids), plus `offset`, `max`,
  `sort`, `order`.
- Expects a **paginated** response `{ data, totalCount }` — `totalCount` is required, not optional:
  `pages = Math.ceil(totalCount / pageSize)` (`useTableData.jsx:82-83`); a missing `totalCount`
  yields `NaN` pages and breaks pagination.

catalog-service's T2 list (`ProductSupplierController.java:27-30`) is **unfiltered, unpaginated,
unsorted, and returns `{ data }` only**.

**Decision (user-approved):** the list-query support lands as its **own backend-only sub-task,
sequenced before the cutover task** — not folded into the cutover. It matches the backend +
integration-tests mold of reshaped T3-T5 (same gate/review cadence), gives an independently
verifiable unit, and keeps the cutover focused on its unique frontend + routing + e2e work. The
cutover depends on this backend already existing, so an explicit prior task makes the dependency
clear.

Scope of this sub-task:

- Filtering by `product`, `supplier`, `defaultPreferenceTypes`.
- Pagination via `offset`/`max`, returning `{ data, totalCount }`.
- Sorting via `sort`/`order`.
- Integration tests over the real list-page param/response shapes (not synthetic).

## 6. The 401 mechanism (accurate description)

The misleading 401 is **not** a direct exception→401 map. An unhandled
`DataIntegrityViolationException` (e.g. `Column 'product_id' cannot be null`) propagates out of the
handler → Spring Boot forwards the request to `/error` → that internal dispatch re-enters the
security filter chain, hits `anyRequest().authenticated()` with
`HttpStatusEntryPoint(HttpStatus.UNAUTHORIZED)` (`SecurityConfig.java:25,27`) → **401**.

A `@RestControllerAdvice` `@ExceptionHandler` catches the exception **in-dispatcher**, so there is
no `/error` forward, no second pass through the security chain, and no spurious 401 — the honest
4xx is returned instead. The §3.2 fix relies on exactly this: handle before the forward.

## 7. Cluster-end cutover task (after T5 and the list-query sub-task)

Once T2-T5 and the list-query backend exist in catalog-service, one cutover task switches the
frontend seam:

- **Form load → client-side join.** Replace the single nested Grails GET with separate flat GETs
  assembled in the form: product name via catalog's owned `GET /api/product/{id}`; supplier and
  manufacturer names from the denormalized `supplierName`/`manufacturerName` columns the flat DTO
  already carries.
- **Form save → flat.** Rewrite the save payload builders to send flat keys (`productId`,
  `supplierId`, `manufacturerId`, …) to each catalog endpoint.
- **List page → catalog.** Point the list page at the catalog list-query endpoint (§5).
- **Attributes stay on Grails.** `ProductSupplierAttribute` is not among the migrated entities;
  the form's attributes save continues to hit Grails. nginx must repoint the cluster
  (`/api/productSuppliers`, package, preferences endpoints) **without** capturing
  `/api/productSupplierAttributes`.
- **nginx repoint** for the whole cluster, re-enabling the parked e2e.
- **Tests = Option C:** both a Playwright UI-driving test (exercises the real form/list in a
  browser) **and** an API-shape e2e (asserts the flat request/response contract).

## 8. Out of scope

- **T6-T11** (the other migrated entities) — zero React callers, no form to break; unaffected.
- **Phase-5 write entities** (e.g. `Tag` M:N) that may exhibit the same break — explicitly
  **wait-and-see**; a possible **Phase 5.6**, not this scope (user decision).
- **`ProductSupplierAttribute` migration** — stays on Grails.
- **SPA decoupling / webpack→index.html** — remains Phase 12 (parent design A19).
