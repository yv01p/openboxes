# Phase 5.1 Horizontal Cleanup Slice — Design Spec

## Goal

Address the Phase 5 retrospective's A+B+C backlog (16 items) across 10 SDD tasks plus a light done-gate, tagging `phase-5.1-cleanup` when done. Headline scope: extract the duplicated JWT authentication infrastructure across 5 Spring Boot services into a Spring Boot Auto-Configuration starter (`services/jwt-auth-common`). Bundle: 9 RC codifications across 3 process docs + 2 C-cleanups + 4 post-tag toolchain/CI carry-in items.

Operationalizes the Phase N.1 horizontal-cleanup pattern Phase 4.1 established: Phase N tags vertical-slice deliverables per CIR-clean plan; Phase N.1 tags horizontal cleanup spanning Phases 1..N codebase. Without N.1, retro candidates accumulate unboundedly under "Phase X = graveyard"; with N.1, debt is a bounded follow-on commitment.

## Background

Phase 5 (catalog-service modular extraction) closed at `phase-5-catalog` (moved post-retro from initial `f410e0549` to `c5f531851` to include 11 RC-26 L2 husky/lint-staged follow-up commits). The retrospective triaged 26 candidates via Categories A-F (see retro §"Process meta-lessons 7"). Plus 4 net-new "Phase 5.1 candidate" items emerged from the post-tag carry-in cascade (node engine, React peer-dep, package-lock discipline, L1+L2 lint-defense codification).

### Anchor counts
- **A** (codify-the-lesson): 9 items — RC-1, RC-2, RC-3, RC-4, RC-5, RC-7, RC-8, RC-24, RC-25
- **B** (accumulating debt extraction): 1 headline — RC-9 (JWT triple copy → starter library)
- **C** (1-line atomic cleanups): 2 items — RC-11, RC-12
- **Post-tag carry-in**: 4 items — node engine bump, React peer-dep, package-lock regenerator discipline, L1+L2 lint-defense codification

Total: 16 items addressed across 10 SDD tasks + 1 done-gate. Phase 4.1 absorbed 13 items in 6 tasks; Phase 5.1's larger task count reflects the per-service split for jwt-auth-common consumers (T2 batches 3 canonical services; T3 + T4 each handle a per-service-divergent migration).

## Approach

**Vertical-first, per Phase 4.1 mirror.** jwt-auth-common extraction (headline + load-bearing) lands first while design context is fresh. Doc codifications follow grouped by destination file (not by RC number), so each codification task touches exactly one process doc. Post-tag toolchain carry-in lands next as its own batch (different surface area — frontend/CI vs Java/Spring). C-cleanups slot in as one batched task. Light done-gate per Phase 4.1 — no full T12 ritual because Phase 5.1 is mostly docs + a single shared Java module, not a new service slice.

**Full SDD review cadence (belt & suspenders, overrides retro's light-cadence recommendation).** Rationale: starter-library shape decision is non-trivial (Auto-Configuration ordering, conditional beans, multi-service consumer surface); jwt-auth-common is load-bearing for all 5 services' auth path — a regression breaks every service simultaneously; toolchain bumps (node, Gradle node plugin, React) have cascade risk per RC-26 history.

- **CDR** (critical-design-review) on this spec after user approves it; iterate until clean.
- **CIR** (critical-implementation-review) on the implementation plan after thorough-writing-plans produces it; iterate until clean.
- User-enforced stop-after-each-task gate cadence inherited from Phase 4/5.
- Two-stage per-task review (spec-compliance + code-quality) per established cadence.

### Approaches rejected
- **De-risk-first** (toolchain bumps before extraction): jwt-auth-common touches Java/Gradle/Spring Boot, not the node/npm pipeline — different surfaces, no risk transfer. Delays headline value for no risk reduction.
- **Codification-first**: lessons are all from Phase 5, already retro'd; nothing forgets faster by waiting two days. Optimizes for a problem that doesn't exist.

## Architecture

Four pieces of new infrastructure. The first is load-bearing; the others are bounded.

### 1. jwt-auth-common Spring Boot Auto-Configuration starter

**Module layout.** New `services/jwt-auth-common/` Gradle subproject (sibling to the 5 service dirs inside `services/`). Maven coordinates `org.openboxes:jwt-auth-common:0.1.0-SNAPSHOT` (inherited from `services/build.gradle` `allprojects { group = 'org.openboxes'; version = '0.1.0-SNAPSHOT' }`). Package: `org.openboxes.auth.common`.

Files:
- `JwtCookieAuthFilter.java` — the canonical 50-line shape extracted from catalog/location/organization (byte-identical except package per A1). Delegates parsing to `JwtService`. Includes T7-M1 logging discipline (catch JwtException; `logger.debug("JWT cookie rejected: " + e.getClass().getSimpleName())`) so all consumers inherit the security comment without copy-pasting it.
- `JwtService.java` — the canonical 29-line shape: `validate(String) → Map<String, Object>` + `COOKIE_NAME = "obx_token"` constant + HMAC secret injection via `@Value("${openboxes.jwt.secret}")`.
- `JwtAuthAutoConfiguration.java` — `@AutoConfiguration` class. Declares `@Bean JwtService` and `@Bean JwtCookieAuthFilter` conditional on `openboxes.jwt.secret` property being set (`@ConditionalOnProperty(name = "openboxes.jwt.secret")`).
- `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` — single line pointing at `org.openboxes.auth.common.JwtAuthAutoConfiguration` (Spring Boot 3.x discovery mechanism).
- `build.gradle` — minimal: depends on `spring-boot-starter-security` + `io.jsonwebtoken:jjwt-api/impl/jackson:0.12.5` (matches A2-verified version).

**Auto-Configuration ordering.** Annotate `JwtAuthAutoConfiguration` with `@AutoConfigureBefore(SecurityAutoConfiguration.class)` to ensure the filter bean exists before any service's `SecurityConfig` reads from `HttpSecurity`. Per A7: exact annotation target (vs `SecurityFilterAutoConfiguration` or `SpringBootWebSecurityAutoConfiguration` — Spring Security 6.x has multiple candidates) verify-at-implementation via integration test confirming filter bean is reachable from SecurityFilterChain wiring; switch annotation target if first attempt doesn't land the bean correctly.

**settings.gradle update.** Add one line to `services/settings.gradle`: `include 'jwt-auth-common'`. The root `settings.gradle` (Grails) is NOT touched.

**Per-service migration.** Each consumer:
- Add `implementation project(':jwt-auth-common')` to its `build.gradle` (1 line).
- Delete the 3 local files (`JwtCookieAuthFilter`, `JwtService`, the filter-wiring lines in `SecurityConfig`).
- `SecurityConfig.java` reduces to its HttpSecurity chain only (+ per-service `permitAll` routes if any); starter wires the filter bean automatically.

## Risks

- **Auto-Configuration ordering bites all 5 services simultaneously.** If `JwtAuthAutoConfiguration` loads after a service's `SecurityConfig`, the filter bean isn't available when HttpSecurity wires. Mitigated by `@AutoConfigureBefore(...)` annotation (exact target verified at implementation per A7) + integration test per service in T2/T3/T4 (existing `*ServiceIntegrationTest` patterns already exercise the 401-on-missing-JWT path per A16).
- **identity-service issuer/validator split is non-trivial.** Splitting `JwtService` (47 lines combining `issue()` + `validate()`) into `JwtIssuerService` (issuer side, stays) + starter's `JwtService` (validator side, extracted) risks breaking the `chooseLocation` re-issuance flow. Mitigated by: T3 reads `chooseLocation` callers first (per A6: AuthController.java:45-50 → AuthService.chooseLocation() → jwtService.issue() at lines 69+101); existing integration tests `chooseLocation_reissuesJwtAndUpdatesLastLoginDate` etc. provide regression coverage.
- **document-service T7-M1 logging discipline regression.** If the starter's filter doesn't preserve the class-name-only logging on `JwtException`, we silently regress on a security-relevant behavior. Mitigated by: T1 starter implementation copies the T7-M1 logic verbatim from document-service's filter; T4 verifies via deliberate bad-token request + log inspection.
- **Gradle node plugin bump is a 5-year, 6-major-version jump.** Plugin v1.5.3 → v7.0.1 likely has configuration-block + task-name changes. Mitigated by: T8 runs `./gradlew :npm_run_bundle` standalone after the bump; if the task name/syntax changed, the failure is immediate and bounded to T8.
- **Multi-service auth simultaneous deployment.** Phase 5.1 doesn't add new services or new auth pathways; it consolidates existing ones. But all 5 services migrate to depend on the new starter. If the starter has a subtle defect, ALL 5 services regress at once. Mitigated by: T2-T4 split per-service with TestContainers + Playwright per task; each commit independently revertible; CI runs the full E2E suite on every push.
