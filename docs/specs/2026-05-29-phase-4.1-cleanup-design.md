# Phase 4.1 Horizontal Cleanup Slice — Design Spec

## Goal

Address the 13-item A+B+C retrospective backlog from Phase 4 across 6 scoped SDD tasks plus a light done-gate, tagging `phase-4.1-cleanup` when done. Operationalize the Phase N + Phase N.1 separation pattern: Phase N tags vertical-slice deliverables per CIR-R3 plan; Phase N.1 tags horizontal cleanup (cross-cutting debt + recurring patterns the vertical work revealed) spanning Phases 1..N codebase. Without N.1, retro candidates accumulate unboundedly under "Phase X = graveyard"; with N.1, debt is a bounded follow-on commitment.

## Background

Phase 4 (organization-service modular extraction) closed at `phase-4-organization` (commit `65d645321`) with 24 retrospective candidates surfaced. The retrospective triaged them into Categories A-F (see retro §"Process meta-lesson 3"):
- **A** (codify-the-lesson): 3 items — meta-process changes, no code-functionality change
- **B** (accumulating debt): 2 items — duplication that grows with each phase if not extracted
- **C** (1-line atomic cleanups): 5 items — trivial spec-faithful fixes
- **D** (intentional Grails parity): 4 items — DELETED from backlog with documented rationale
- **E** (true Phase X defer): 6 items — legitimate "later" items with explicit deferral reasons
- **F** (defensible style decisions): 2 items — DELETED with rationale

Net: 13 items addressed in Phase 4.1 (A+B+C); 6 deleted in Phase 4 retro (D+F); 6 deferred to true Phase X (E).

## Approach

Selected approach: **6 SDD tasks split by category** + **1 light done-gate task** + tag, **all under a single `phase-4.1-cleanup` tag**, with the user-enforced stop-after-each-task gate cadence inherited from Phase 4. Light done-gate (Playwright re-run + nginx reload smoke + tag) rather than full T12-style ritual because Phase 4.1 is mostly docs + small refactors; no service-side code changes warrant the heavy JUnit re-run + 15-min soak.

Alternative approaches considered and rejected:
- **T10.5 sandwich inside Phase 4**: rejected during T10 disposition (user picked Phase 4.1 separation for cleaner boundaries).
- **All A+B+C in one giant commit**: rejected for revertibility — per-category commit enables targeted revert if any one piece breaks.
- **Defer everything to true Phase X**: rejected because Categories A (recurrence-prevention) and B (accumulating debt) get strictly worse over time.

## Architecture

Phase 4.1 introduces three new types of project infrastructure:

### 1. Codified-lessons infrastructure (Category A)

New project-root `CLAUDE.md` (auto-read by Claude Code at session start per official behavior) pointing to a new `docs/process/` directory containing structured lesson files:
- `docs/process/README.md` — index of lesson files
- `docs/process/sdd-reviewer-checklist.md` — JPA SINGLE_TABLE nullability rule (RC-1) + future reviewer items
- `docs/process/plan-template-defects.md` — T12 plan defects (RC-22)
- `docs/process/plan-ordering-rules.md` — compose-modifying-task ⇒ CI-workflow-task ordering rule (RC-2)

Phase 5+ planning sessions (which start by loading CLAUDE.md → docs/process/) inherit these lessons automatically. Future phases append to these files rather than starting fresh-graveyard lists in retros.

### 2. Shared E2E auth fixture (Category B item 1, RC-3)

New `e2e/fixtures/` directory containing `auth.ts` with a single `login(request)` helper for the default-credential `/api/identity/login` flow. JSDoc on the helper documents its intended use (default `E2E_USER`/`E2E_PASSWORD` env vars) and deviation guidance (specs needing non-default credentials POST inline). 3 specs migrate to use the fixture: `organization-service.spec.ts` (Phase 4), `location-service.spec.ts` (Phase 3), `identity-caller-regression.spec.ts` (Phase 2). One spec (`identity-password-reset.spec.ts`) is deliberately NOT migrated because its NEW_PWD usage doesn't fit the default-credential helper signature; a breadcrumb comment in that spec marks the exception with grep-discoverable reference back to the fixture.

### 3. Shared nginx headers include (Category B item 2, RC-11)

New `docker/nginx/conf.d/proxy_params` file (no `.conf` extension — not auto-loaded by nginx's `include /etc/nginx/conf.d/*.conf;` directive) containing the standard `proxy_set_header Host $host; proxy_set_header X-Forwarded-For $remote_addr; proxy_set_header Cookie $http_cookie;` triplet. All 8 blocks in `app.conf` that share the byte-identical proxy_set_header triplet migrate to `include /etc/nginx/conf.d/proxy_params;` directive — 6 Spring Boot service routes (identity, documents, location×2, organization×2) plus 2 Grails-facing catch-all routes (`/api/` Grails API catch-all, `/openboxes/` GSP catch-all). RC-10 (nginx block-ordering convention comment) is merged into this same task to avoid two app.conf edits across tasks.
