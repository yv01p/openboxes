# Phase 5.5 Catalog-deferred Slice — Retrospective

## TL;DR

Phase 5.5 migrated the **10 deferred catalog entities** (Phase 5 FD#5 / RC-10) to catalog-service plus Category writes (RC-11 breadcrumb trigger), and partially cleaned the Grails CategoryApi (RC-13, 3 of 5 refs). Seven entities shipped GET-only per the T1 per-entity audit (zero React write callers): ProductCatalog (T6), ProductCatalogItem (T7), ProductAttribute (T8), ProductAssociation (T9), ProductComponent (T10), UnitOfMeasureConversion (T11), plus ProductAttribute's read filter. The **ProductSupplier write-cluster** (ProductSupplier T2, ProductSupplierPreference T3, ProductPackage T4, ProductPrice T5) carried the only real React write paths and consumed the bulk of the phase's risk. Category writes (T12) were the single FD#3 write task on the Phase-5-shipped Category entity. UnitOfMeasureConversion, ProductCatalog/Item use the FD#6 cache-with-refresh pattern.

The headline of the phase was **not the per-entity migrations — it was the ProductSupplier cutover, which exposed that the migration had been proven against synthetic payloads, not the real SPA contract.** The initial T2 nginx repoint broke the live Product Sources form because the catalog write path had only ever been exercised with JSON hand-shaped to the new flat DTO — never with the request the React form actually sends or the response shape it actually reads. That regression forced a mid-phase course correction: **C1** reverted the T2 nginx repoint (forward commit, not amend), **C2** added a catalog `@RestControllerAdvice` so write failures return honest 4xx instead of a `/error`-forwarded spurious 401, **C3** codified the lesson (`docs/process/synthetic-payload-blind-spot.md`), and a **net-new write-contract-reconciliation design + plan** superseded the original "cutover is frontend-only" premise. The cutover (CUT) was then executed last, against real payloads, and its C3 ground-truth pass uncovered **three further backend gaps** the plan assumed didn't exist — list-item enrichment (LQ2), package upsert + default-link (PKG-FIX), and an attribute read-filter + Jackson-strict payload mismatch — all fixed and proven by a seeded round-trip e2e.

## What worked

- **The C3 "real-payload ground-truth" discipline paid off three times in one task.** After the synthetic-payload regression (RC-43) was codified at C3, the CUT task opened by tracing the ACTUAL save/load round-trip against the real DTOs/services BEFORE writing code. That pre-check is what surfaced LQ2 (the flat list DTO omitted 6 columns the live Grails list serves — the Preference Type column would have crashed on `undefined.length`), PKG-FIX (the catalog ProductPackage save was create-only and never linked the default package → broken round-trip; the form POSTs the package on both create and edit), and the attribute-load + Jackson-strict mismatch (the form would have fetched the whole `product_attribute` table, and the package payload carried fields not in `ProductPackageDto` → 400). None of the three were in the plan; all three would have shipped broken under a "cutover is just wiring" execution. The lesson the phase keeps teaching: **a frontend-facing migration is proven only against the request the SPA sends + the response shape it reads.**

- **C1 revert-forward (not amend) kept the T2 history honest.** When the T2 nginx repoint broke the live form, C1 (`70b8d6f23`) reverted the routing as a NEW forward commit and parked the through-nginx e2e (`test.skip`) until the cluster-end cutover, rather than amending T2 to pretend it was clean. The catalog-service ProductSupplier backend stayed in place. Audit trail shows exactly what was caught and when. Same convention that held through Phases 3–5.

- **The mid-phase design/plan replacement was the right call, not scope creep.** The original catalog-deferred plan's premise — "CUT switches the React seam + nginx; the write-cluster (T2–T5) is already complete" — was empirically false. Rather than patch the cutover task, the phase wrote a dedicated **write-contract-reconciliation design** (`dc8d2ff22`) + **plan** (`bdc167a1d`, full replacement) that made the flat catalog contract the source of truth and moved the React seam to it, with §5 list-query and §7 cutover detail. Two CDR/CIR rounds hardened it. Treating a wrong premise as a design defect (re-spec) rather than an implementation detail (hack the task) is what kept the cutover correct.

- **The per-task STOP gate caught every forced decision before code.** Each of the three CUT-discovered gaps was escalated to the user as a load-bearing decision (enrich-backend vs accept-degradation for LQ2; backend-upsert + both-verifications for PKG-FIX; add-backend-filter for the attr load). The user chose the thorough fix every time. The gate cost ~30s/task; it bought three correct architectural decisions that a continuous-execution run would have made silently.

- **The seeded round-trip e2e was the only thing that actually proved the write path** — and it caught a stale container too. With `openboxes-db` holding 0 products/suppliers, the standard write/UI e2e self-skip (suite convention), so save-path correctness rested entirely on code review + the catalog integration tests until `catalog-product-supplier-roundtrip.spec.ts` seeded a minimal fixture (product/uom/party/preference_type), drove the real flat payloads, and asserted `defaultProductPackageId` set + derived pricing + preferences + upsert. That spec ALSO surfaced that the deployed catalog container was stale (built before LQ2/PKG-FIX). Empty-DB e2e green ≠ write path works (RC-45).

- **GET-only entity clones (T6–T11) were clean, low-risk, and fast.** Six entities followed the Phase-5 GET-only template (entity / flat FK-only DTO / repo / read-service / controller + per-task nginx + Playwright smoke). T10 (ProductComponent) was "the cleanest entity in the set — no special cases, no Grails-vs-live deviation." The T1 audit's "zero React callers → default GET-only" cascade (FD#1) held for all seven, exactly as the Phase-5 T1 audit cascade did. Net-new GET surface with zero blast radius.

- **JPA-audit infra built once at T2, reused by T3/T4/T5/T12.** FD#8 Option-A (`JwtAuditorAware` reading the JWT `sub` from the SecurityContext + `@EnableJpaAuditing` + `@EntityListeners` full-User audit) was built at T2 and reused across the write-cluster + Category. The forecast-in-a-breadcrumb pattern from Phase 5.1 (RC-11) closed cleanly: `CategoryCache.refresh()` reopened to `public` at T12 exactly when `CategoryService.save()` landed.

- **Codify-mid-stream (RC-25) applied again at C3.** The synthetic-payload lesson was codified to `docs/process/synthetic-payload-blind-spot.md` at `03ce0fcfd` the moment it was understood, not deferred to this retro — so it was already in force as the CUT ground-truth discipline that found the three gaps. The clearest possible proof a codify-mid-stream paid off: the rule caught bugs later in the same phase.

## Codebase / env gotchas (Phase 6+ should know)

- **catalog-service Jackson is strict by default** (`FAIL_ON_UNKNOWN_PROPERTIES=true`, no override in `application.yml`). Any payload field not on the target DTO → 400. The ProductPackage save payload originally carried `minOrderQuantity`/`eachPrice`/`tieredPricing`; the fix routed `minOrderQuantity` to the DETAILS payload (where `ProductSupplierDto` persists it) and made the package payload DTO-exact. Phase 6 write paths must keep frontend payloads DTO-exact OR add an explicit Jackson leniency config. (RC-46.)

- **ProductPrice price-VALUE fields are write-only on GET.** `ProductPackageDto.from()` maps `productPackagePrice`/`contractPricePrice`/`contractPriceValidUntil` as always-null on GET — they are write-only inputs. The form load recovers prices via `GET /api/productPrices/{id}` for the package's `productPriceId` AND the supplier's `contractPriceId`. `contractPriceValidUntil` ↔ `ProductPrice.toDate` (no `valid_until` column).

- **ProductPrice has no collection endpoint — by design.** `ProductPriceController` exposes only `@GetMapping("/{id}")` (prices are written through `POST /api/productPackages` and read by-id during the cutover). Bare `GET /api/productPrices` has no handler → Spring forwards to `/error` → the re-dispatched JWT filter yields a **spurious 401** (not 404/405). The React form never calls the bare collection, so this is cosmetic — but it is a real edge of the C2 advice (which maps exceptions in-dispatcher; the no-handler `/error` forward on a path catalog doesn't serve is outside that scope). (RC-47.)

- **`ProductSupplier` does NOT map a `productSupplierPreferences` @OneToMany collection.** Preferences are a separate entity with a `productSupplier` @ManyToOne FK; load them by FK (`findByProductSupplierIdIn`), never expect a mapped collection. The LQ2 list-enrich batch-loads preferences in a SECOND query, NOT in the paginated `@EntityGraph` (collection + `Pageable` = in-memory-pagination pitfall).

- **The flat catalog list query has a sortable allowlist with a `dateCreated` fallback** for unmapped sorts (no `PropertyReferenceException`/500). The frontend still sets `sortable:false` on non-allowlisted columns (e.g. productName) for correct UX. `totalCount` is required in the list envelope or the list page computes `pages=NaN` (A6).

- **Grails build requires Temurin 8 (RC-20 / `d9dbf96da`).** `JAVA_HOME=/usr/lib/jvm/temurin-8-jdk-amd64 ./gradlew <task>` from repo root; under default JDK 21 the Grails Gradle 4.10.3 build crashes + hangs. catalog-service (`cd services && ./gradlew ...`) uses default JDK 21. The two builds have split JDK toolchains — codified at `docs/process/dev-env-setup.md`. Running `./gradlew :catalog-service:test -p services` from the repo ROOT invokes the Grails gradlew → BUILD FAILED; always `cd services` first.

- **The flat-contract NAME problem (FD#2 consequence, accepted).** Flat catalog DTOs carry denormalized `supplierName`/`manufacturerName`/`productName` but NOT cross-service names — so the list's created-by/updated-by user names and a preference's destinationParty (org) name render ids, not names. preferenceType/uom names ARE resolved client-side from redux options. FD#2 forbids cross-service name resolution; this degradation is documented + accepted. (RC-48.)

- **The handoff-prior `app.conf:906` productSupplierAttributes Grails sub-route was a STALE claim** — there is no such block; `/api/productSupplierAttributes/batch` rides the `/api/` catch-all to Grails (T1-confirmed, T14 re-verified). The cutover correctly added NO productSupplierAttributes block. Codebase comments are meticulous about `file:line`; keep cross-refs current or omit line numbers.

## Process / meta-lessons

1. **A "cutover" task that flips the seam must re-verify the entire write-cluster round-trip against real payloads — it is never frontend-only.** The phase's central error was treating CUT as wiring on top of a "complete" T2–T5 write-cluster. The cluster was NOT complete: the package save was create-only and unlinked, the list DTO was missing 6 columns, and the read paths assumed a whole-table fetch the strict-Jackson backend would reject. The plan, the design, and the per-entity tasks all missed these because none of them exercised the real save→reload→list→edit round-trip. **Lesson: a cutover is a verification task, not a wiring task. Its first step is a real-payload ground-truth trace of the full round-trip, and it owns fixing whatever that trace reveals — even backend gaps the upstream tasks were assumed to have closed.** (RC-44.)

2. **An empty database hides every write path, and "all green" on an empty DB is a false negative.** `openboxes-db` has 0 products/suppliers, so the entire write/UI e2e surface self-skips. The phase nearly shipped the cutover with the package round-trip broken because empty-DB e2e was green AND the integration tests (ddl-auto=create, their own seed) didn't model the live form's two-POST sequence. The seeded round-trip e2e — which seeds a minimal fixture, drives the real flat payloads through nginx, and self-cleans — is what proved the path AND caught a stale deployed container. **Lesson: for any write-path migration against an empty live DB, a self-seeding round-trip e2e exercising the real SPA payloads is mandatory; do not accept skip-heavy green as proof.** Strong candidate for a `docs/process/` lesson doc (empty-DB-hides-write-paths + stale-container trap). (RC-45.)

3. **Synthetic payloads shaped to the new DTO prove nothing about a frontend-facing migration.** (Codified at C3 → `docs/process/synthetic-payload-blind-spot.md`.) The T2 regression's root cause was that the catalog write path was only ever tested with JSON hand-shaped to the flat DTO — the exact shape the new code expects — never the request the legacy React form sends (different field names, nested vs flat, extra fields) or the response shape the form reads. Synthetic tests are circular: they confirm the code parses what the code emits. **Lesson: migration proof must originate from the consumer — capture the real request/response, then assert the new backend honors it.** This is now the C3 discipline that the rest of the phase ran on. (RC-43.)

4. **Re-spec a wrong premise; don't hack the task.** When the cutover premise proved false, the phase wrote a fresh reconciliation design + plan (full replacement, two review rounds) rather than bolting fixes onto the cutover task. The cost was one design+plan cycle mid-phase; the benefit was that CUT executed against a correct, reviewed contract instead of accreting ad-hoc patches. **Lesson: a falsified load-bearing assumption is a design defect — route it back through brainstorming/plan, not through the implementer.**

5. **Per-task STOP + real-payload ground-truth compose into a strong gate.** The gate cadence (Phases 3–5) plus the C3 discipline meant every CUT gap was (a) discovered by a ground-truth trace before coding and (b) dispositioned by the user before any change landed. The two disciplines reinforce: ground-truth surfaces the forced decision, the STOP gate ensures a human picks. Neither alone would have caught all three CUT gaps cleanly.
