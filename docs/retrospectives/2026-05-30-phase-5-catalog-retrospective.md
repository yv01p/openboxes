## Codebase / env gotchas (Phase 5.5+ should know)

### Schema & JPA

- **CHAR vs VARCHAR + TINYINT vs BIT divergence pattern now confirmed across 5 of 5 services.** Production schema uses `CHAR(38)` for entity `@Id` columns (which @GeneratedValue default would Hibernate-validate-fail without `length=38` on `@Column` or `columnDefinition="CHAR(38)"`) and `TINYINT(3)` for boolean fields (which Java `Boolean` would Hibernate-validate-fail without `columnDefinition="TINYINT"` since Hibernate maps Boolean to `bit(1)` by default). Phase 5 hit this at T4 for `Category.is_root` and `Tag.is_active`. Same pattern previously surfaced at every service phase (`document-service` Phase 1, `identity-service` Phase 2, `location-service` Phase 3, `organization-service` Phase 4). **Codify** in plan-template T4 step + `docs/process/sdd-reviewer-checklist.md`: before declaring any `Boolean` field with no `columnDefinition`, run `SHOW COLUMNS FROM <table> LIKE '<column>'` and verify the DB type. (Phase 5.1 candidate.)

- **`@ElementCollection` inner-column names — 5 of 5 plan-text guesses were wrong at T4.** Plan-text optimistically guessed `activity_code` / `field_code` / `option_value` for ProductType's `supportedActivities`/`requiredFields`/`displayedFields`/`reportingActivities` element collections; actual DB columns are `product_activity_code` / `product_field` / etc. (verified post-failure via `DESCRIBE product_type_supported_activity` etc.). `ddl-auto: validate` caught all 5 at first T4 smoke (this trap is recoverable, unlike nullability divergence which `validate` silently passes). **Codify** in plan-template: for any `@ElementCollection` table, run `DESCRIBE <table>` BEFORE writing the plan to get exact inner column names. The convention `<owning_entity>_<field>` is NOT reliable. (Phase 5.1 candidate.)

- **Synonym DB nullability divergence with Grails domain.** Grails `Synonym` domain declares `locale(nullable: false)` + `synonymTypeCode(nullable: false)`; production DB has both as nullable VARCHAR(50). T4 entity removed `nullable=false` to match DB (per the Phase 4 RC-1 lesson — codified in `docs/process/sdd-reviewer-checklist.md`). FD#10's deferred service-layer validator will need to enforce non-null + uniqueness at the app layer if/when Synonym writes ever land (Phase 5.5+ scope per spec §6). Tracked as Phase X.

## Process / meta-lessons

1. **The "5th copy" inflection is a strongly-motivated extraction trigger.** Phase 4 retro flagged JWT triple-copy as "STRONGLY MOTIVATED" at the 4th copy; Phase 5 made it the 5th copy with a clean 3-line Direct-apply at T5 (`dbdb21378`). The clean execution itself is the evidence: a starter library wrapping `JwtCookieAuthFilter` + `JwtService` + `SecurityConfig` skeleton can absorb all 5 services without per-service customization to lose (because there isn't any). Phase 5.1 should ship this. The general lesson — **a duplication that propagates cleanly across N services has no per-service variance, which is exactly the precondition for safe extraction.** Don't wait for the 6th copy.

2. **Codify-mid-stream beats defer-to-retro for clear-target lessons.** Rule 3 codification landed at `7291864fc` immediately after T9's nginx fix, not bundled into this T13 retro. The codification took ~5 min. The benefit: Phase 5.5+ plan-writers (and reviewers) see the rule at plan-write time. Test: every Phase 5.5 plan-write or T8-nginx-style task that consults `docs/process/plan-ordering-rules.md` and avoids the regression IS the evidence Rule 3 paid off. Codify-mid-stream is appropriate when: (a) the lesson has a clear codification target file, (b) the recurrence risk is concrete and bounded, (c) capturing inline doesn't bloat the active phase. Defer-to-retro is appropriate when: (a) the lesson needs cross-RC pattern-matching to formulate, (b) the target file doesn't exist yet, (c) the lesson is meta-process not single-rule. Both have their place; pick deliberately.

3. **Reviewer "independent reproduction" beats reviewer "code reading" at finding false-bug framings.** T10's "production caching limitation" framing read plausibly from the test-comment standpoint — the test failure WAS real, the reflective `clearCaches()` fix WAS correct. What the framing got wrong was the root-cause attribution. Independent prod-stack curls (5 sequential `/api/productType` requests after a catalog restart, all returning 200 with populated `supportedActivities`) are what proved the production behavior was correct and the failure was test-isolation-only. **Lesson for code-quality reviewers**: when a fix's commit body asserts "this is a production bug" OR "production has limitation X", reproduce X against the running prod stack BEFORE accepting the framing. Code-reading alone can validate the patch shape but not the root-cause claim. Codify as a code-reviewer checklist item? Phase 5.1 candidate.

4. **Per-task gate held value at T9 and T10; rubber-stamp passes acceptable.** 13 tasks × ~30s gate overhead = ~7 min of "controller surfaces finding, user picks disposition". 2 of those gates substantively changed direction (T9 nginx-currencies fix-now; T10 false-bug-framing retraction). 4 of those gates were Light-SDD-direct-apply approvals (T5, T8-follow-up, T10-follow-up, T11-follow-up — see What worked #5). The remaining 7 were rubber-stamp "continue". Same cost/benefit balance as Phase 3/4; the 2 real fix-now decisions justify the entire overhead.

5. **Plan-text method/identifier names are suggestions, not contracts.** T6 plan-code blocks named service methods `service.listUom()` / `service.listUomClass()`; T6 implementer renamed to `listUoms()` / `listUomClasses()` (plural per Java collection-returning-method convention). T7 implementer caught the divergence before wiring controllers. **Plan defect**: plan-template should annotate where method names are placeholder vs binding. Or, more bluntly, plan-writers should pick names that match the convention so implementers don't need to rename. (Phase 5.1 candidate; same plan-template-defects.md target as T2 + T12 items.)

6. **T1 audit's "DO NOT delete" gate prevented a real regression.** Per-controller §6 audit identified 3 deletable controllers (Attribute, Category, UnitOfMeasure) but flagged each as "conditional on final-grep at T9 time". T9 implementer ran the final greps; Category was kept due to 5 non-React refs (integration tests + `runtime.groovy:757` fillRate filter + `UrlMappings.groovy:45,49` explicit mappings + `SecurityInterceptor.groovy:23` exclusion list); UnitOfMeasure kept due to `currencies()` action. If T9 had blindly deleted all 3 per the §6 "DELETE candidate" column, the fillRate filter would have broken silently and the integration tests would have gone red. **Lesson**: audit recommendations with conditional gates are GOOD design; implementers MUST honor the conditional checks rather than collapsing to the optimistic count. This generalizes — Phase 5.5's per-entity audit will surface similar conditional-delete gates and the same discipline applies.

7. **The Phase 4 retro RC-table model scales.** 25 RCs this phase vs 24 last phase. A-F triage applied to all 25 without ambiguity, generating clear dispositions: 7 FIXED (4 follow-up commits + 1 mid-stream Rule-3 + 2 satisfied by Phase 4.1 carry-forward), 3 DELETED with rationale (D+F), 1 codify-now, 8 to Phase 5.1 or 5.5, 6 to true Phase X. Without the framework, the 25 would have piled into an unbounded Phase X queue. With the framework, 10 of 25 have explicit fix-or-delete dispositions this phase + 9 have explicit forward-phase assignments + 6 have explicit deferral rationale. **The Phase 4.1-invented "Phase N.1 horizontal cleanup" model has earned permanent retention** — Phase 5.1 will pick up the B/C carryover from this retro plus any incidental cleanup the jwt-auth-common extraction surfaces.
