## 6. Step 6 — FD#8 audit-field-pattern FORCED DECISION (RESOLVED — Option A; see disposition at end of section)

> **THIS SECTION SURFACES A FORCED DECISION FOR THE USER. T1 DOES NOT PICK.** The human will disposition this at the T1 review gate. Both options are documented with a clear recommendation and the *verified* jwt-auth-common mechanism.

**Empirical antecedent (PA8) — re-verified at this HEAD:**
```bash
grep -rln "AuditingEntityListener|EnableJpaAuditing|AuditorAware|@CreatedDate|@LastModifiedDate|@CreatedBy|@LastModifiedBy" services/
→ (zero matches)
```
**NO existing service in `services/` uses Spring Data JPA's auditing pattern.** Additionally verified: catalog-service currently reads **no** `userId` anywhere (`grep` over `services/catalog-service/src/main` for `getAttribute("userId")` / `SecurityContextHolder` / `RequestContextHolder` → zero), `CatalogServiceApplication.java` is a bare `@SpringBootApplication` (no `@EnableJpaAuditing`), and **no production Java anywhere in `services/` writes `created_by`/`updated_by`**. → FD#8's "reuse an existing pattern" antecedent is **false**; its fallback **fires**. A forced decision is required.

### Verified jwt-auth-common mechanism (grounding for Option A)

Read `services/jwt-auth-common/src/main/java/org/openboxes/auth/common/JwtCookieAuthFilter.java`. On a valid JWT cookie, the filter (`doFilterInternal`) does **both** of the following, so the authenticated user id is available via TWO grounded paths:

1. **Request attribute** — `req.setAttribute("userId", userId)` at **`JwtCookieAuthFilter.java:38`** (also sets `"locationId"`:39 and `"roleIds"`:40). `userId` is the JWT `sub` claim (`JwtCookieAuthFilter.java:34`).
2. **Spring SecurityContext** — `SecurityContextHolder.getContext().setAuthentication(new UsernamePasswordAuthenticationToken(userId, null, authorities))` at **`JwtCookieAuthFilter.java:42–43`**. The principal name (`Authentication.getName()`) **is** the same `userId` string.

catalog-service already wires this filter via `SecurityConfig.java:26` (`addFilterBefore(jwtFilter, …)`), so both paths are live in every authenticated request today. An `AuditorAware<String>` can therefore read the user id with **no new plumbing** — the cleanest standard-Spring path is `SecurityContextHolder.getContext().getAuthentication().getName()` (the canonical Spring Data JPA `AuditorAware` idiom); the request-attribute path (`RequestContextHolder` → `getAttribute("userId")`) is the documented alternative the plan's PA8 named.

### Option A (RECOMMENDED) — build the audit-listener pattern in catalog-service NOW

Scope:
- `@EntityListeners(AuditingEntityListener.class)` on the **4 full-audit** entities (ProductSupplier, ProductSupplierPreference, ProductPackage, ProductPrice — see §8) with `@CreatedDate`/`@LastModifiedDate`/`@CreatedBy`/`@LastModifiedBy` fields.
- `@EnableJpaAuditing` on `CatalogServiceApplication.java`.
- A new `AuditorAware<String>` bean (e.g. `services/catalog-service/src/main/java/org/openboxes/catalog/audit/JwtAuditorAware.java`) returning the user id from `SecurityContextHolder.getContext().getAuthentication().getName()` (falling back to `Optional.empty()` when unauthenticated — populates `created_by_id`/`updated_by_id` as NULL for system/anonymous writes, which the Grails columns already tolerate as nullable, see §8).
- The **5 timestamp-only** entities (ProductCatalog, ProductCatalogItem, ProductAssociation, ProductComponent, UnitOfMeasureConversion) get `@EntityListeners(AuditingEntityListener.class)` with only `@CreatedDate`/`@LastModifiedDate` (no `@CreatedBy`/`@LastModifiedBy`). ProductAttribute gets none (no audit fields, see §8). ProductAssociation special-cases `Instant` timestamps (not `Date`/`Timestamp`) — AuditingEntityListener supports `Instant` natively.

Rationale: populates the existing `created_by_id`/`updated_by_id`/`date_created`/`last_updated` columns correctly from day one (parity with Grails `beforeInsert`/`beforeUpdate` which set `createdBy`/`updatedBy` from `AuthService.currentUser`); the mechanism is verified-present (above) with zero new auth plumbing; it's the idiomatic Spring path and sets the reusable pattern future services adopt. Cost: ~1 new bean + 1 annotation on the app class + per-entity annotations (low).

### Option B — postpone audit fields to a later phase

Scope: T2–T11 omit `@CreatedBy`/`@LastModifiedBy` (and possibly `@CreatedDate`/`@LastModifiedDate`); the `created_by_id`/`updated_by_id` columns populate as NULL on catalog-service writes. Build the auditing pattern in a dedicated later phase.

Rationale: smaller per-task surface now; defers the (small) infrastructure decision. Cost: catalog-service writes lose audit-user provenance (NULL `created_by_id`/`updated_by_id`) for the interim — a data-quality regression vs the Grails writer, and a later backfill/migration risk.

### Recommendation

**RECOMMENDED: Option A.** The blocking concern behind FD#8's fallback (no existing pattern to copy) is cheap to resolve because the jwt-auth-common user-id mechanism is verified-present and already wired into catalog-service's filter chain — Option A is a ~1-bean lift that preserves Grails-parity audit provenance and establishes the canonical pattern. Option B trades that small lift for a NULL-provenance data-quality gap.

**USER DISPOSITION (T1 review gate, 2026-05-31): Option A — build the audit-listener pattern now.** T2 creates the `JwtAuditorAware` `AuditorAware<String>` bean (reading `SecurityContextHolder.getContext().getAuthentication().getName()`, returning `Optional.empty()` when unauthenticated) + adds `@EnableJpaAuditing` to `CatalogServiceApplication.java` + the per-entity audit annotations on ProductSupplier; T3–T5 (full-audit) and T12 (Category timestamp-only) reuse the established pattern; the 5 timestamp-only entities get `@CreatedDate`/`@LastModifiedDate` only; ProductAttribute gets none.
