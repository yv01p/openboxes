## 2. Literal-wrongness findings

### 2.1 LQ `defaultPreferenceTypes` filter via JOIN multiplies rows and inflates `totalCount`

- **Description.** Task LQ Step 1 specifies the preference-type filter as "join `product_supplier_preference` on `product_supplier_id` filtering `preference_type_id IN (:types)`". A `ProductSupplier` with two preferences whose types both fall in `:types` produces **two** joined rows. With a `Pageable`/`Page` over that join, the page content contains the duplicate supplier and `page.getTotalElements()` counts it twice. The list page then shows duplicate rows and computes `pages = Math.ceil(totalCount / pageSize)` (A6/PV15) from an inflated `totalCount` — wrong page count. The spec's stated outcome for §5 ("filtering by `defaultPreferenceTypes`; returning `{data, totalCount}`") is literally wrong whenever a matched supplier has more than one matching preference.
- **Evidence.** Plan LQ Step 1 ("join `product_supplier_preference` … `preference_type_id IN (:types)`"); `product_supplier_preference` is many-per-supplier (`ProductSupplierPreference.groovy:20` `ProductSupplier productSupplier`; no 1:1 constraint). `useTableData.jsx:82-83` derives pages from `totalCount`.
- **Proposed fix.** Make the filter non-multiplying: `WHERE EXISTS (SELECT 1 FROM ProductSupplierPreference p WHERE p.productSupplier = ps AND p.preferenceTypeId IN :types)` (or `SELECT DISTINCT` with a matching `countDistinct`). Add an LQ integration test that seeds a supplier with **two** matching preferences and asserts it appears once with `totalCount = 1`.

### 2.2 CUT breaks the list page: flat rows vs. nested table accessors, missing product name, and an unsortable column

- **Description.** Task CUT Step 3 ("Point the list page at the catalog list-query endpoint; confirm the param names and `{data,totalCount}` match") repoints the list to the flat catalog response but does not touch the list *table* component, which reads nested accessors and offers a sort the flat entity can't satisfy:
  1. `ProductSupplierListTable.jsx` columns use nested accessors `product.productCode` (:60), `product.name` (:68), `supplier.displayName` (:133). The flat catalog list returns flat fields (`productCode`, `supplierName`, `supplierCode`); these nested accessors resolve to `undefined` → the Product-Code, **Product-Name**, and Supplier columns render blank post-cutover.
  2. The flat `ProductSupplierDto` carries `productCode` but **no product name** (PV16); the LQ response is a list of those flat DTOs. The sortable "Product Name" column (`product.name`, :68) therefore has no data source at all on the list — it cannot be populated by a per-row `GET /api/product/{id}` the way the single-record form can (that would be N fetches per page).
  3. `supplier.displayName` is a **sortable** column (:133, no `sortable:false`). Clicking it sends `sort=supplier.displayName` (the hook sends `tableState.sorted[0].id`, PV15). The flat `ProductSupplier` entity has **no `supplier` association** (`supplierId`/`supplierName`/`supplierCode` are raw columns, PV8/PV16) → Spring Data builds the `Sort` and throws `PropertyReferenceException: No property 'supplier' found` → 500 → `/error` forward → spurious **401** (the exact §6 trap C2 fixes elsewhere but does not cover here, because `PropertyReferenceException` is not in C2's handled set).
- **Evidence.** `src/js/components/productSupplier/ProductSupplierListTable.jsx:60,68,133` (nested accessors; `supplier.displayName` sortable); `useProductSupplierListTableData.jsx:11` (`defaultSorting.sort='dateCreated'`) + PV15 (`sort = tableState.sorted[0].id`); flat entity/DTO field list (PV8/PV16 — no `supplier` property, no product name). Plan CUT File Structure lists `useProductSupplierListTableData.jsx` but **not** `ProductSupplierListTable.jsx`; CUT Step 3 does not mention accessors, product name, or sort-field mapping.
- **Proposed fix.** Bring `ProductSupplierListTable.jsx` into CUT's Modify set and rewrite its accessors to the flat fields (`productCode`, `supplierName`/`supplierCode`); decide how the list obtains **product name** (denormalize a `productName` into the LQ response — LQ already has the `product` association in hand and can map `ps.product.name` — or drop/relabel the Product-Name column); and map the sortable column ids to valid entity sort properties (see §2.4) so `supplier.displayName` becomes `supplierName`, `product.name`/`product.productCode` become joined `product.name`/`product.productCode` (valid only because `product` *is* a `@ManyToOne`).

### 2.3 Association-id → entity mapping cannot live in `applyTo()` (T4/T5)

- **Description.** Tasks T4 and T5 instruct: "populate `defaultProductPackageId` / `contractPriceId` in `ProductSupplierDto.from()`/`applyTo()`". The `from()` (entity→DTO) direction is fine. But `applyTo()` (DTO→entity) maps flat scalars and has **no repository access**, while the target entity fields are `@ManyToOne ProductPackage defaultProductPackage` / `@ManyToOne ProductPrice contractPrice` — you cannot assign a `String` id to a `@ManyToOne` field. Setting these from the flat `*Id` strings must happen in the **service** write path via a repository resolve (mirroring T2's `resolveProduct(...)` → `getReferenceById`). As written, an executor following the step literally either does not compile (assigning `String` to `ProductPackage`) or wrongly injects a repository into the DTO record, breaking the established T2 mapper pattern.
- **Evidence.** `ProductSupplierDto.applyTo()` (lines 40-61) sets only scalars + `tieredPricing`/`active`; comment lines 38-39 explicitly: association ids "are ignored in T2 (associations don't exist on the entity yet)." T2's id→entity resolution lives in `ProductSupplierService.resolveProduct(...)` (PV10), not the DTO.
- **Proposed fix.** Reword T4/T5: `from()` maps `entity.getDefaultProductPackage()?.getId()` → `defaultProductPackageId`; the **service** `save`/`update` resolves `defaultProductPackageId`/`contractPriceId` to entity references via `getReferenceById` (add `resolveProductPackage`/`resolveProductPrice`, mirroring `resolveProduct`) and sets them on the entity. `applyTo()` stays scalar-only.

### 2.4 T3 app-layer pair-uniqueness check mishandles null `destinationParty` and within-batch duplicates

- **Description.** Task T3 Step 5 enforces pair-uniqueness via `findByProductSupplierIdAndDestinationPartyId(psId, destId)` "before insert … if a different row exists, throw `DuplicatePreferenceException`." Two gaps make the check a silent no-op on real paths:
  1. `destinationParty` is **nullable** (PV13, `destinationParty(nullable: true …)`). A derived query `…AndDestinationPartyId(psId, null)` generates SQL `destination_party_id = NULL`, which is never true → a null-destination preference never matches an existing null-destination row → unlimited null-destination duplicates per supplier slip through, contradicting the GORM `unique:['productSupplier']`-on-`destinationParty` invariant the spec says T3 ports app-layer.
  2. The check queries the committed DB per item; two items in the **same `saveOrUpdateBatch` payload** sharing a `(productSupplier, destinationParty)` pair both see "no existing row" (the sibling isn't flushed) → both insert.
- **Evidence.** `product/ProductSupplierPreference.groovy:21` (`destinationParty` nullable) + `:41` (`unique:['productSupplier']`); plan T3 Step 5/Step 6 (per-item DB check inside the batch loop). A9 establishes no DB unique index backstops either gap.
- **Proposed fix.** Branch the query on null (`…AndDestinationPartyIsNull` when `destinationPartyId == null`); and de-dup within the batch in memory before/while inserting (track seen `(productSupplier, destinationParty)` pairs in the batch). Add integration tests for both (a null-destination duplicate and a same-pair-twice batch).

### 2.5 Reshaped T3/T4/T5 cannot prove their entity mapping against the live schema — the C3 blind spot, re-introduced

- **Description.** §4/§3.3 of the source design exist *because* T2's tests (synthetic payloads, `ddl-auto=create`) passed while the real write path was broken; the plan codifies that lesson in C3. Yet the reshaped T3/T4/T5 are "backend + integration tests only" with **no e2e** (the cutover owns the seam), and the integration harness runs `spring.jpa.hibernate.ddl-auto=create` (PV14) — Hibernate **generates** the schema from the entity, so a wrong column name, wrong type, or a missing/incorrect `@Version` on `product_supplier_preference`/`product_package`/`product_price` is masked (the generated schema always matches the entity). The first time these entities meet the **real** Grails-owned schema is service boot under production `ddl-auto=validate` (caught only at T14's smoke) or CUT's e2e — so a mapping error surfaces at CUT/T14 with a root cause up to four tasks back, and the per-task review gate (§4) cannot catch the one failure class this whole reconciliation is about.
- **Evidence.** Plan C3 (the lesson); §4 ("No per-task through-nginx e2e"); PV14 (`ddl-auto=create`); the T2 commit message's own note that `ddl-auto=create` "cannot catch a missing version mapping, e2e real-DB POST is the proof." The Liquibase shadow changelogs use `tableExists` MARK_RAN (no column assertions), so they do not validate column mappings either.
- **Proposed fix.** Give T3/T4/T5 a real-schema mapping proof that does not wait for CUT: e.g., a per-task integration test (or CI step) that applies the Grails/Liquibase schema and boots catalog-service with `ddl-auto=validate` against it (so a column/`@Version` mismatch fails the task), or an explicit per-task real-DB smoke `POST`/`GET`. If the team accepts deferring the proof to CUT/T14, say so explicitly in T3/T4/T5 so the "per-task review gate" claim is honest about what it cannot verify.

## 3. Forced decisions

### 3.1 Repoint shared `ProductApi.getProduct` vs. add a form-local catalog product fetch (CUT)

- **The choice.** CUT Step 1 needs the product *name* for the form and says: "Repoint `ProductApi.getProduct` from `/api/generic/product/{id}` … OR add a dedicated catalog product fetch — pick the minimal change." The plan does not pick.
- **Why it's forced.** `productApi.getProduct` is **shared**: it is consumed by `src/js/hooks/productSupplier/form/useProductSupplierForm.js` **and** `src/js/utils/option-utils.jsx` (2 consumers). Repointing it globally from the Grails generic endpoint (`${GENERIC_API}/product/${id}`, `ProductApi.js:19`) to the catalog `/api/product/{id}` changes the response shape for `option-utils.jsx`'s callers too (Grails generic vs. catalog flat product DTO differ). So "pick the minimal change" is a real either/or with a cross-consumer blast radius, not a free choice. PV25 already deferred exactly this to a "CUT pre-check" — it needs an owner's decision, not an executor's guess.
- **The options.** (a) Repoint `getProduct` globally to catalog `/api/product/{id}` and verify `option-utils.jsx`'s consumers tolerate the catalog product shape (audit + possibly adapt them). (b) Leave `getProduct` on Grails generic and add a separate form-local catalog product fetch used only by `useProductSupplierForm.js` (no blast radius, small new code). (c) Some hybrid (e.g., a new `getCatalogProduct` used by both, migrated deliberately).
