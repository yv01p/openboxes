## 2. Literal-wrongness findings

### 2.1 LQ `JOIN FETCH ps.product` + `Pageable` will fail the derived count query

- **Description.** The round-1 fix (now in LQ Step 1) specifies `JOIN FETCH ps.product` to carry product name without an N+1, while LQ returns `Page<ProductSupplier>` (Step 2). A Spring Data `@Query` (or `JpaSpecificationExecutor` with `root.fetch(...)`) that combines a `JOIN FETCH` with a `Pageable`/`Page` return needs a separate **count query** that does **not** contain the fetch. Spring Data's auto-derived count query chokes on the fetch join (Hibernate rejects a fetch in a count/scalar query, or the derivation produces invalid JPQL), so the repository method throws at bootstrap/execution → the list endpoint 500s → `/error` → spurious 401. So the list page (in scope per §5/§7) is broken by the very fix added to populate its product-name column.
- **Evidence.** Plan LQ Step 1 ("`JOIN FETCH ps.product` so the list response can carry product name (Step 2) without an N+1") + Step 2 (`returning ... page.getTotalElements()` over `Page<ProductSupplier>`). Spring Data JPA: a fetch join with `Pageable` requires an explicit `countQuery` (for `@Query`) and is disallowed in a `Specification` count query (`UnsupportedOperationException: query root not allowed to fetch during count`).
- **Proposed fix.** Fetch `product` via `@EntityGraph(attributePaths = "product")` on the paginated repository method instead of a JPQL `JOIN FETCH` — Spring Data then builds a correct, fetch-free count query automatically. (If a custom `@Query` is kept, it must also declare an explicit `countQuery` without the fetch.) Add this as the mechanism in LQ Step 1 so the executor doesn't implement the naive fetch-join-with-Pageable that fails.

### 2.2 The cutover makes `POST /api/productPackages` a ProductPrice write path, but no task implements that persistence

- **Description.** The form's save fan-out posts the package section via `productPackageApi.save(packagePayload)` (CUT Step 2 keeps this hop → catalog T4 `POST /api/productPackages`). `buildPackagePayload` puts **price data** in that payload: `contractPricePrice`, `contractPriceValidUntil`, and the package's own price fields (`fixedPrice`/`packageSpecification`). Per the design's own §1, `ProductPrice` "is persisted via the package endpoint's payload." So at cutover the package POST must create/update (a) the package's `ProductPrice` (`ProductPackage.productPrice`) and (b) the supplier's contract `ProductPrice` and set `ProductSupplier.contractPrice` to it. The plan does **not** wire this: T4's POST scope omits `productPrice` (deferred to T5), and T5 explicitly states "writes are Grails/embedded only (no React write caller) → … the cutover uses **GET-by-id**" and "service provides `save`/`update` for completeness." That framing is true pre-cutover but **false at cutover** — the package endpoint becomes the React write path for `ProductPrice`. As written, the package POST persists the package but silently drops `contractPricePrice`/`contractPriceValidUntil`/package-price, so editing a supplier's price/contract price no longer saves — breaking the form's stated save outcome.
- **Evidence.** `src/js/hooks/productSupplier/form/useProductSupplierForm.js:265-277` (`buildPackagePayload` returns `contractPricePrice`, `contractPriceValidUntil`, `...fixedPrice`, `...packageSpecification`), `:318-323` (`productPackageApi.save(packagePayload)`); design `2026-05-31-…-write-contract-reconciliation-design.md` §1 ("ProductPrice … persisted via the package endpoint's payload"); plan Task T5 Verb-scope bullet ("writes are Grails/embedded only (no React write caller) → … cutover uses GET-by-id"); plan Task T4 ("`productPrice` is OMITTED at T4 … T5 appends it") with no price-persistence step in either task's POST.
- **Proposed fix.** Make the ProductPrice write path explicit for the cutover: have T4/T5 specify that `POST /api/productPackages` persists the embedded prices from the payload — create/update `ProductPackage.productPrice` from the package price, and create/update the supplier's contract `ProductPrice` and set `ProductSupplier.contractPrice` (the `contractPricePrice`/`contractPriceValidUntil` fields) — with an integration test asserting a package POST carrying price fields persists both the package and its `ProductPrice` rows. Correct T5's "no React write caller / read-only at cutover" wording accordingly (it is a write caller via the package endpoint after CUT). Also confirm whether `validUntil` is a real `ProductPrice` column (already flagged as a T5 execution check, PV16) — the contract-price write needs it.
