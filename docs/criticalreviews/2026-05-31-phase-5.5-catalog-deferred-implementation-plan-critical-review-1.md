## 2. Literal-wrongness findings

**Finding 1: T2 Step 2 entity references types created in T4 + T5 — `javac` will fail at T2's own gate.**

- Description: T2 Step 2 code (plan lines 272-278) declares two `@ManyToOne` fields in `ProductSupplier.java`:
  - `@ManyToOne(fetch = FetchType.LAZY) private ProductPrice contractPrice;` (`// catalog-internal; created in T5`)
  - `@ManyToOne(fetch = FetchType.LAZY) private ProductPackage defaultProductPackage;` (`// catalog-internal; created in T4`)

  `ProductPrice.java` is created in **T5** and `ProductPackage.java` is created in **T4**, both later than T2. T2 Step 13 (line 410-414) invokes `cd services && ./gradlew :catalog-service:test`, which runs `javac` over `ProductSupplier.java`. Java has no forward declarations; `javac` requires referenced types to exist at the importing file's compilation time. T2 cannot pass its own Step 13 gate (`cannot find symbol: class ProductPrice` and same for `ProductPackage`).

  The plan acknowledges this at line 309: "T2's `ProductSupplier.contractPrice @ManyToOne ProductPrice` declared in T2 references this T5 type — T2's commit places a forward declaration; T5's commit completes the type. JPA compile-validated at T5 build time." This wording is incorrect about Java semantics: `javac` runs at T2 build time and will fail there; "JPA compile-validated at T5 build time" conflates JPA's runtime entity-mapping validation (which happens at EntityManagerFactory init) with Java source compilation (which happens unconditionally on every build).

  Since T2 is the canonical template that T3-T11 derive from, leaving this unresolved blocks every subsequent task too (T3, T5, T8 depend on T2's commit landing).

- Evidence:
  - Plan lines 272-278 (T2 code block declaring `@ManyToOne ProductPrice` + `@ManyToOne ProductPackage`)
  - Plan line 309 (plan's own "forward declaration" note that doesn't resolve the issue)
  - Plan line 410-414 (T2 Step 13 invokes `./gradlew :catalog-service:test` which performs `javac` compilation)
  - Plan line 444 (T4 entry: "ProductPackage entity migration")
  - Plan lines 451-459 (T5 entry: "ProductPrice entity migration (depends T2 + T4)")
  - Java Language Specification §7.5 (import declarations) — type must be visible at translation unit's compile time

- Proposed fix (pick one):
  - **(a) Reorder the per-entity sequence so PP/Price precede PS.** T4 → T5 → T2 → T3 → T6 → T7 → T8 → T9 → T10 → T11. Note: T5 has a `belongsTo = [productSupplier]` per Grails A4, so the JPA T5 entity also wants `@ManyToOne ProductSupplier productSupplier` — meaning T5 also has a forward ref to T2. The dependency forms a cycle in the @ManyToOne graph. Cannot trivially linearize with strict `@ManyToOne` typing throughout.
  - **(b) Split the bidirectional declarations across the dependent tasks.** T2 creates ProductSupplier WITHOUT the `contractPrice` and `defaultProductPackage` fields; T4's per-task scope is extended to add `defaultProductPackage` to ProductSupplier (one extra Modify line); T5's per-task scope is extended to add `contractPrice` to ProductSupplier and to declare `productPackage` + `productSupplier` `@ManyToOne`s on ProductPrice (the latter is already in T5's body). This preserves T2's commit numbering and per-task revertibility.
  - **(c) Use raw `@Column` string FK IDs in T2 and upgrade to `@ManyToOne` in the dependent tasks.** Cheaper to implement but loses JPA-managed bidirectional graph for those two refs until upgraded. Same fix idea as (b) but typed differently.

  Option (b) reads as the cleanest match for the plan's stated per-task revertibility discipline; the canonical T2 template body should drop the two forward-ref `@ManyToOne` lines and add an explicit note that T4 + T5 add them.

**Finding 2: T2 Step 7 Liquibase shadow changelog code block diverges from the established Phase-5 pattern in 4 ways, one of which (`onFail`) changes startup behavior in dev/prod.**

- Description: T2 Step 7 example XML (plan lines 354-365) uses `<preConditions onFail="HALT">` and omits the `logicalFilePath` attribute, the `<comment>` element, and the established `onFailMessage` text. It also uses `author="phase-5.5"` and id `phase5.5-shadow-create-product-supplier`. The existing Phase-5 shadow changelogs (verified at `services/catalog-service/src/main/resources/db/changelog/changelog-shadow-create-product.xml:8-9` and `services/catalog-service/src/main/resources/db/changelog/changelog-shadow-create-category.xml:8-9`) use:

  ```xml
  <databaseChangeLog ...
                     logicalFilePath="services/catalog-service/db/changelog/changelog-shadow-create-<entity>.xml">
      <changeSet id="phase5-shadow-create-<entity>" author="openboxes-catalog">
          <preConditions onFail="MARK_RAN" onFailMessage="<entity> table not found — Grails Liquibase must run first">
              <tableExists tableName="<entity>"/>
          </preConditions>
          <comment>
              Shadow for <entity> table. Grails Liquibase owns table creation.
              catalog-service uses spring.jpa.hibernate.ddl-auto=validate to prove entity-mapping correctness.
          </comment>
          <!-- No body: table already exists per the precondition. -->
      </changeSet>
  </databaseChangeLog>
  ```

  Functional impact:
  - In integration tests this doesn't bite: `spring.liquibase.enabled=false` (verified at `CatalogServiceIntegrationTest.java:38`). Tests skip Liquibase entirely; Hibernate `ddl-auto=create` builds the schema.
  - In dev/prod, with `onFail="HALT"`, if catalog-service starts before the Grails monolith has finished its own Liquibase migration (or in a fresh DB, partial restore, or container-ordering race), the `tableExists` precondition fails and Liquibase **aborts the entire master changelog** — catalog-service refuses to start. With `MARK_RAN`, the same precondition failure gracefully records the changeSet as already-run and proceeds; catalog-service starts and the JPA `ddl-auto=validate` (or runtime entity init) will produce the right error if the table is genuinely missing.
  - The plan's own File Structure section (line 27) states intent: "Liquibase shadow changelog with `tableExists tableName="<snake_table>"` precondition + empty body **per Phase 5 pattern**" — the code block contradicts this stated intent.
  - T2 is the canonical template (plan line 152: "see T2 for the canonical step set; T3-T11 narrate ONLY the deltas from T2"), so a defect in T2's template propagates to all 10 per-entity tasks plus T12.

- Evidence:
  - Plan lines 354-365 (T2 Step 7 example XML using `onFail="HALT"`, missing `logicalFilePath`, missing `<comment>`, author `phase-5.5`, id format `phase5.5-shadow-...`)
  - `services/catalog-service/src/main/resources/db/changelog/changelog-shadow-create-product.xml:1-17` (Phase-5 pattern)
  - `services/catalog-service/src/main/resources/db/changelog/changelog-shadow-create-category.xml:1-17` (second instance of Phase-5 pattern)
  - `services/catalog-service/src/test/java/org/openboxes/catalog/CatalogServiceIntegrationTest.java:38` (`spring.liquibase.enabled=false` in tests)

- Proposed fix: Replace T2 Step 7's XML example with one matching the Phase-5 pattern verbatim:
  - `onFail="MARK_RAN"` with descriptive `onFailMessage="product_supplier table not found — Grails Liquibase must run first"`
  - Add `logicalFilePath="services/catalog-service/db/changelog/changelog-shadow-create-product-supplier.xml"` to `<databaseChangeLog>`
  - Add a `<comment>` child matching the established two-line text
  - `author="openboxes-catalog"`
  - `id="phase5-shadow-create-product-supplier"` (no decimal in `phase5`)

  Optionally add a single sentence in the T3-T11 "deltas only" narration confirming "Step 7 follows T2's revised pattern verbatim" so the SDD subagent doesn't regress to the broken template.
