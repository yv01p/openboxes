## 2. Literal-wrongness findings

### 2.1 T1's `services/jwt-auth-common/build.gradle` will fail `./gradlew :jwt-auth-common:build` as designed

**Description.** `services/build.gradle` declares a `subprojects { apply plugin: 'org.springframework.boot' ... }` block (verified at services/build.gradle:16-19 during A2 verification). Every subproject inherits the Spring Boot plugin, which auto-creates a `bootJar` task that requires a `main()` class. A library module (no `@SpringBootApplication`, no main class) fails `bootJar` with a "Main class name has not been configured" error. The spec's T1 description ("build.gradle — minimal: depends on `spring-boot-starter-security`, `io.jsonwebtoken:jjwt-api/impl/jackson`") does not include the boilerplate needed to disable bootJar for a library subproject. T1's validation gate ("Build green on `cd services && ./gradlew :jwt-auth-common:build` standalone") cannot pass as specified.

**Evidence.** services/build.gradle:14-30 (`subprojects` block applies Spring Boot plugin unconditionally); Spring Boot 3.x plugin docs (bootJar enabled by default; requires main class).

**Proposed fix.** §4.1's T1 file list adds to `services/jwt-auth-common/build.gradle`:
```gradle
bootJar { enabled = false }
jar { enabled = true }
```
Alternative: restructure `services/build.gradle` subprojects block to apply Spring Boot plugin only to subprojects that need it (e.g., move the `apply plugin: 'org.springframework.boot'` from `subprojects {}` to each of the 5 service `build.gradle` files individually). The first option is local and lower-risk; the second is cleaner but expands T1's blast radius to all 5 service build.gradle files.

### 2.2 T3 MODIFY file enumeration omits 2 files that contain `jwtService.issue(...)` references requiring rename

**Description.** Spec T3 lists 4 MODIFY files: `build.gradle`, `SecurityConfig.java`, `JwtIssuerService.java` (renamed), `CookieService.java`. The rename of identity's `JwtService` → `JwtIssuerService` also requires updating two other files that hold live references to `jwtService.issue(...)`:

- `services/identity-service/src/main/java/org/openboxes/identity/service/AuthService.java:69` and `:101` — both lines call `jwtService.issue(user, locationId, roleIds)`. These are the actual issuer callers (login + chooseLocation flows per spec A6).
- `services/identity-service/src/test/java/org/openboxes/identity/IdentityServiceIntegrationTest.java:404` — calls `jwtService.issue(u, locationId, roleIds)` as test helper.

After T3's rename, the field type (`JwtService jwtService`) is gone in both files; compilation fails until the field type + variable name are updated (or remain as `jwtService` if only the type is changed and `@Autowired` does its job). T3 as written cannot reach a green build state, blocking done state #1 (commit lands), done state #4 (Playwright pass), and done state #6 (per-service auth smoke).

**Evidence.** grep `jwtService\.issue\|JwtService.*issue` returned 4 hits during A6 verification: `AuthService.java:69`, `AuthService.java:101`, `IdentityServiceIntegrationTest.java:404`, plus the JwtService declaration itself.

**Proposed fix.** T3 MODIFY column gains 2 entries (`AuthService.java`, `IdentityServiceIntegrationTest.java`); count updates from 4 to 6. T3 description acknowledges the full rename surface: "Rename `JwtService → JwtIssuerService`; update all 3 in-service consumers (AuthService, CookieService, IntegrationTest)".

### 2.3 File-count inconsistency: spec claims 9 deleted files but only 8 are actually deleted

**Description.** Three places in the spec assert "9 deleted local JWT files":

The last item is a modification of `SecurityConfig.java`, not a deletion — the spec's "Known issues / accepted as out of scope" section explicitly says SecurityConfig.java stays per-service ("NOT extracting a default SecurityFilterChain bean from starter ... keeps SecurityConfig per-service"). ### 2.4 Done state #8's find pattern matches the new starter's JwtService.java and won't return the claimed result

**Description.** Done state #8 specifies: `find services -name 'JwtCookieAuthFilter.java' -o -name 'JwtService.java'` should "return only `JwtIssuerService.java` (renamed)". This pattern is wrong on two fronts:

(a) After T3's rename, `JwtIssuerService.java` exists — but it does NOT match `-name 'JwtService.java'` (different filename). So `JwtIssuerService.java` cannot appear in this find's output regardless of design state.

(b) The starter created in T1 lives at `services/jwt-auth-common/src/main/java/org/openboxes/auth/common/JwtService.java`. After all 10 tasks complete, this file exists and matches the find pattern. The pattern would return ONE result (the starter's `JwtService.java`), not zero, not "only `JwtIssuerService.java`".

The done-gate check intent is "no local copies of the canonical files remain in service directories". The pattern needs explicit exclusion of the starter module.

**Evidence.** Spec Done state #8; T1 module layout in §4.1 confirming starter location.

**Proposed fix.** Done state #8 pattern becomes:
```sh
find services -name 'JwtCookieAuthFilter.java' -o -name 'JwtService.java' \
  | grep -v 'services/jwt-auth-common/'
```
Expected output: 0 lines. Or use `find services -path 'services/jwt-auth-common' -prune -o \( -name 'JwtCookieAuthFilter.java' -o -name 'JwtService.java' \) -print`. The done-state language tied to JwtIssuerService.java should also be reworded — it's surfaced by a different check (`find services/identity-service -name 'JwtIssuerService.java'` returning 1 result).

## 3. Forced decisions

### 3.1 T8/T9 ordering vs React peer-dep mismatch

**The choice.** When T8 reverts the husky@8/lint-staged@12 downgrades (i.e., runs `npm install --save-dev husky@^9 lint-staged@^17` or equivalent), the install resolves the full dependency tree under the newly-bumped Gradle-bundled npm (v9.x ships with node 18 per the Gradle node plugin v7 bump in T8). npm v9 enforces strict peer-dependency checking by default. The pre-existing React 16.8.6 + `@testing-library/react-hooks@8.0.1` peer-dep mismatch (which currently requires `--legacy-peer-deps` in CI per T9's scope) causes `npm install` to fail before husky/lint-staged can be added. T8 cannot complete its own validation gate ("`./gradlew :npm_run_bundle` green") under the spec's stated T8-then-T9 ordering without addressing this.

**Why it's forced.** Three independent variables collide inside T8 as designed: (a) npm version bump from v6 (lax) to v9 (strict), (b) husky/lint-staged install requires a full dependency resolution, (c) React peer-dep mismatch is currently masked by --legacy-peer-deps in CI and by npm v6 lax behavior locally. After (a) bumps and (b) runs, (c) surfaces. The spec specifies T8-then-T9 but does not name the resolution.

**The options.**
- **(A) Swap order: T9 before T8.** T9 (React 16.8.6 → 16.14.0) removes the peer-dep root cause first. T8 then runs against a clean dependency tree; husky/lint-staged install succeeds under strict npm 9. CI's `--legacy-peer-deps` removal moves from T9 to T8 (or stays in T9 since T9 is the one removing the React root cause). Mild ordering inversion vs the design's "vertical-first" sequencing.
- **(B) Transient `--legacy-peer-deps` in T8.** Keep T8-then-T9 ordering; T8's `npm install` for husky/lint-staged uses `--legacy-peer-deps` transiently; T9 removes both the React peer-dep root cause AND the CI's `--legacy-peer-deps`. Preserves design ordering; introduces a temporary inconsistency between T8's commit state and the eventual end state.
- **(C) Merge T8 + T9 into one task.** Single commit handles node bump + React bump + husky/lint-staged revert + CI `--legacy-peer-deps` removal atomically. Loses the independent-verification benefit of the per-task split (the spec's rationale for splitting them was "T9 has a constrained but distinct surface that benefits from independent verification").
