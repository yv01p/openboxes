## 3. Forced decisions

### FD-1 — The §3.2 advice exception taxonomy does not cover T3's app-layer pair-uniqueness rejection

**The choice:** how does T3's pair-uniqueness rejection surface as a 4xx, given it does **not** throw `DataIntegrityViolationException`?

**Why it's forced:** §3.2 specifies the `@RestControllerAdvice` handles exactly `DataIntegrityViolationException → 409` and "bad/missing input (e.g. `MethodArgumentNotValidException`, `HttpMessageNotReadableException`) → 400", and explicitly claims this fix is "needed before T3, whose pair-uniqueness rejection must surface as a real 4xx rather than a masked 401."

But `product_supplier_preference` has **no unique index on `(product_supplier_id, destination_party_id)`** — verified: `SHOW INDEX` returns only PRIMARY(`id`) and five non-unique FK BTREE indexes. The spec's own model (§5 / verified gotchas) is that T3 pair-uniqueness is **app-layer-only** (a service/validator check, plus the "one DEFAULT per productSupplier" NULL-handling DBs can't express). An app-layer check rejecting a duplicate throws a business/validation exception of T3's choosing — it cannot throw `DataIntegrityViolationException` (no DB constraint to violate), and it cannot naturally be a `MethodArgumentNotValidException` (that requires a DB lookup of existing rows, not a bean-validation annotation on the request body) or `HttpMessageNotReadableException`. So with the advice exactly as written, T3's pair-uniqueness rejection falls through to the default handler → `/error` forward → masked 401 — the precise failure §3.2 exists to prevent, for the precise case it names.

**The options (spec must name one; reviewer does not pick):**
- **(a)** T3's service throws a custom catalog exception (e.g. `DuplicatePreferenceException`) and §3.2's advice adds a handler mapping it to **409**. (Most faithful to the conflict semantics; requires the advice's handled set to be open-ended, which the spec should state.)
- **(b)** T3 raises a Bean Validation / `MethodArgumentNotValid`-shaped error so the existing **400** path catches it. (Reuses the existing handler but mislabels a conflict as bad-input, and is awkward for a check that needs a DB lookup.)
- **(c)** Add a DB unique constraint so `DataIntegrityViolationException` fires → existing **409** path. (Rejected by the verified model: DBs allow multiple NULL `destination_party_id`, so the "one DEFAULT per productSupplier" rule still needs app-layer enforcement — a DB constraint alone does not deliver the guarantee.)

The cleanest resolution is (a); the spec should either adopt it or explicitly state that the advice's handled-exception set is extended per-task as write paths land, so the "must surface as 4xx" guarantee is actually delivered.
