## 2. Literal-wrongness findings

**2.1 — RC-16's "no working behavior to byte-match" premise is false and would regress a live UI.**

- **Description.** FD#5's risk bullet states: *"the endpoint currently 500s, so there's no working behavior to byte-match; correctness is defined by the ported logic."* The TL;DR / §2 done-state / §8 A11 all repeat the "fix the 500" framing. This drives the implementation to treat RC-16 as a greenfield fix with latitude on payload/semantics. But the endpoint **works for valid facilities and is consumed live** by the React CycleCount product-classification filter. Migrating it under the "no behavior to preserve" premise — wrong response envelope, wrong union/facility-scoping, or changed error contract — silently breaks that filter. This is exactly the synthetic-payload / cutover-is-a-verification-task trap (RC-43/44/45) the project has already been burned by.
- **Evidence.**
  - Working + consumed: `ProductClassificationApiCRUDSpec.groovy:42-52` (200 + correct union for a valid facility); consumer chain `useCycleCountFilters.js:149` → `option-utils.jsx:305-306` (`const { data } = await productClassificationApi.getProductClassifications(facilityId)`) → `ProductClassificationApi.js:5` (`apiClient.get(...)`).
  - Exact behavior to preserve (from the test + service): response envelope `{ data: [{ name: "<abcClass>" }, ...] }`; union of **global** distinct `Product.abcClass` (`ProductClassificationService.groovy:42-48`) with **facility-scoped** distinct `InventoryLevel.abcClass` (`:50-58`, `eq("inventory", facility.inventory)` — `ProductClassificationApiCRUDSpec.groovy:33-35` proves other facilities' classes are excluded); empty-string/null filtered; sorted; deduped; invalid facility → 500 (`:54-58`).
- **Proposed fix.** Reframe RC-16 in the spec as a **behavior-preserving migration of a working, live-consumed endpoint**, not a bug fix. Specifically: (a) delete the "the endpoint currently 500s, so there's no working behavior to byte-match" risk bullet and the "fixes the 500" language; (b) make the existing integration tests (`ProductClassificationApiCRUDSpec`, `ProductClassificationApiListFiltersOutEmptySpec`) the ground-truth contract — **port** them to inventory-service (the spec's "port/retire" should be "port", not "retire"); (c) require the T9 seeded round-trip to seed a valid facility + `abcClass` rows on **both** `Product` (global) and `InventoryLevel` (facility-scoped, incl. a second facility's row that must be excluded) and assert the real CycleCount-filter payload through nginx; (d) decide and document the invalid-facility error contract (preserve 500, or take the `TODO`'s 400 — a deliberate change, not an accident).

## 3. Forced decisions

**3.1 — Keep RC-16 in Phase 6 core, or move it to 6.5 with its sole consumer?**

- **The choice.** RC-16's classification endpoint stays in Phase 6 core vs. moves to Phase 6.5.
- **Why it's forced.** The spec placed RC-16 in core on the rationale "fixes the 500 / freebie / better optics than Phase 3/5's near-zero deletion" (TL;DR, FD#5, §1) — and the user's two brainstorming approvals of "pull RC-16 into core" were made on that rationale. §1 establishes the rationale is false: it is not a bug fix, and its **only** consumer (grep-confirmed: `useCycleCountFilters.js` is the sole caller) is the CycleCount family, which FD#2 defers **entirely to 6.5**. So the spec's inclusion decision rests on a now-falsified premise and should be re-made with correct facts; the codebase constraint (consumer lives in the deferred phase) is what forces the re-decision.
- **The options** (reviewer does not pick):
  - **(a) Keep in core** as a behavior-preserving migration (per §2.1). Still-valid justifications: inventory-service owns `InventoryLevel` so the heavier half of the query goes local; it yields a real Grails deletion (controller + service + DTO + mapping); it exercises the first catalog outbound read. Cost: a live endpoint is migrated a phase ahead of its consumer UI, so the cutover must be proven against the real CycleCount payload while that UI is still Grails-hosted.
  - **(b) Defer to 6.5** with the CycleCount family it serves. Justification: consumer-cohesion — the endpoint and its only consumer migrate together, avoiding a cross-phase split and the standalone-cutover regression surface in core. Cost: the (non-bug) endpoint stays on Grails one more phase; core's deletion bite returns to near-zero (Phase 3/5 shape), so core's value rests entirely on standing up the service + owning 8 tables + resolving ProductAvailability.
